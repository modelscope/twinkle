# 多租户运维

## 部署监控机

1. 申请长期在线的 CPU 监控机，运行 Collector、Tempo、Loki、Mimir 和 Grafana。
   按写入量和查询并发配置 CPU 和内存，根据各信号的实测日增量准备 30 天的持久存储，
   为 WAL 和压缩预留空间。示例使用受支持的本地块存储。平台若提供 NFS，
   先确认内网对象存储，Mimir 的 TSDB 和工作目录仍放在受支持的本地块存储上。
2. 申请 GPU Runtime 到监控机 Collector 的内网 TCP 4317，以及监控机到业务
   Redis 的内网访问。Grafana 绑定管理员网络地址，并在平台入口限制访问来源。
   启用登录，Grafana 和 Redis 的凭证通过部署密钥配置注入。
3. 使用 [cookbook/observability](https://github.com/modelscope/twinkle/tree/main/cookbook/observability)
   的部署配置和 Runtime OTLP 示例。所有 Runtime 进程使用相同的
   `TWINKLE_TELEMETRY_USER_ID_KEY`，它是独立于 `TWINKLE_TOKEN_SALT` 的随机密钥。
   未配置密钥时，按用户归因和 Redis 快照暂停。轮换后会生成新指纹，既有遥测和已归属的
   旧会话继续使用原指纹，直到保留期结束或会话重建。Checkpoint 目录沿用原有规则。

GPU 服务沿用现有业务入口，指标、日志和 Trace 经 OTLP 出站推送。Ray Dashboard
和 Prometheus 抓取排除在一期外，平台后续允许入站抓取时可再评估。多机 Ray 内网组网单独验收。

## Redis 权限

为 Grafana 申请独立账号，连接 Runtime 使用的 Redis 数据库。
配置看板和 ACL 时，三把键都要带上实际的 `persistence.key_prefix`。
以下示例适用于空前缀、Redis 默认数据库。

```text
ACL SETUSER twinkle-grafana reset on >DEPLOYMENT_SECRET ~admin:index:sessions ~admin:index:trainings ~admin:index:sampling +get
```

密码通过平台密钥管理配置。用 Grafana 数据源实查三把运维键，验证同一账号读业务键、
写入以及用 SCAN 或 KEYS 枚举都会被拒绝。Runtime 的清理 leader 按
`metrics_update_interval` 定时刷新，默认每 15 秒刷新。快照含生成时间，
TTL 为三个刷新周期并向上取整到秒。无归属记录显示「未归属」。

## 查看用量和排障

- 看板顶部的 **Current trainings** 显示当前训练的状态、基础模型和用户指纹。
  点击表内的基础模型或训练 ID，按该训练筛选所选时间段的任务日志和 Trace。
  **Training snapshot updated** 显示快照更新时间。`Unavailable` 表示快照不可用。
  有更新时间且表格显示 `No trainings` 时，当前没有训练。如果表格显示 `No data`，
  检查指纹筛选。查已结束训练时，选训练发生的时间段，在 **Recent training activity**
  按基础模型、最后入队时间和短训练 ID 找记录。旧日志可能只有时间和训练 ID。
- **Training task logs** 显示该训练的入队、完成、失败、超时等任务日志。
  点首页 **Task errors in range** 查询失败、超时和拒绝，或点 **Task events by outcome**
  中的结果查看对应日志。展开有 Trace 的日志，点 **View trace** 直接跳转。
  结果计数统计日志事件，一次任务可产生多条记录。
  旧版 Runtime 的日志可从对应 Trace 的 **Logs for this span** 按任务 ID 查询。
- **User fingerprint prefix** 留空查看全部用户。可直接粘贴图例的 12 位指纹前缀，
  或从 Trace 的 `twinkle.user_id` 复制完整指纹。
  指纹筛选同时作用于指标、Trace 和 Redis 明细。
  **Base model** 按部署的基础模型筛选用量和时延，**Training ID** 筛选任务日志和 Trace。
  无 Token 请求优先用稳定的客户端 ID 计算指纹，缺少客户端 ID 时归到同一个匿名指纹。
- 只对受理的 `forward`、`forward_only`、`forward_backward`、`step`、`clip_grad_and_step`、
  `optim_step` 和普通 `sample` / `asample` 计一次。输入 Token 数复用入队时已知的
  数量，尚未编码且没有 token ID 的输入记为零。运行秒数是各任务的执行时长之和，
  单位为任务秒。看板以窗口内最后一次采样的累计值减去窗口开始前的累计值。
  窗口内新出现的时间序列从零计。心跳、结果轮询和 Runtime HTTP 429 单独查看。
- 用量阈值只在部署配置中设置。Grafana 先汇总各副本和模型的五分钟速率，再按指纹覆盖
  或默认阈值计算和高亮水位。业务受理继续使用原有副本限流规则。
- 在看板的 **Runtime task traces** 按训练 ID 查看任务链路。已知 Trace ID 时，
  可在 **Explore → Tempo** 中直接查询。
  有任务 ID 时，在 TraceQL 编辑器输入 `{ span.twinkle.request_id = "req_..." }`。
  SDK 复用 HTTP 请求 ID 时，可查 `span.twinkle.http_request_id` 并限定时间和操作名。
  点开 `task_queue.execute`，查看 Token 指纹 `twinkle.user_id`、排队时间
  `twinkle.wait_seconds`、执行时间 `twinkle.execution_seconds` 和最终任务状态。失败时遥测记录错误类型。
  Runtime HTTP 耗时截至本次响应，异步任务的结果轮询另计。
- 在 `task_queue.execute` 点 **Logs for this span**，按任务 ID 查询附近的 Runtime 日志。
  看板顶部的 **Find training logs** 直接打开当前选中的训练日志。查看整个服务时，
  在 **Explore → Loki** 选择对应时间段。
  已知服务名和任务 ID 时，使用 `{service_name="服务名"} |= "req_..."`。
  入队和任务完成日志可能分别出现在不同 Trace 上下文中，任务 ID 可把它们对起来。
- **Drilldown → Traces** 按服务等属性汇总 span 的速率、错误和耗时。选择 **All spans**
  可包含 `task_queue.execute` 等子 span。Tempo 从启用 local-blocks 处理器之后收到的
  Trace 生成这类汇总。更早的 Trace 可以继续在 **Explore** 查询。
  **Drilldown → Logs** 按服务和标签浏览日志，适合先找出日志量或错误突增的服务和时间段。
- 队列深度来自 `sum by (deployment) (twinkle_queue_depth)`。GPU 面板按节点和 UUID
  查看物理卡的利用率和显存。在执行 span 的 **Links** 打开 **Node GPU utilization**
  或 **Node CPU utilization** 可查看该实例所在节点和对应时间段的资源曲线。
  新 Trace 的 Resource attributes 也会显示 `twinkle.node`。
  同节点 worker 使用共享的本机临时目录选出 CPU 和 GPU 指标上报进程。RSS 仍按进程上报。
  确认模型与设备独占关系后再把整卡用量归到模型。
- **Last Runtime metric received** 显示各上报节点最近一条指标心跳距今多久。
  心跳消失时检查 Runtime、Collector 及两者的连通性。日志和 Trace 的接收情况分别到 Loki 和 Tempo 核查。

## 发布验收

确认 Runtime 的指标、日志和 Trace 实际到达后端，核对三个后端的 30 天保留配置，
并在重启后查询已保存样本。验证 Grafana 登录、管理员网络限制、Redis 账号权限及实测
节点和 GPU 标识。单独发布可观测改动前，使用线上 Twinkle 和 Tinker SDK 经现有 Mesh
链路验证会话、心跳、采样和异步结果领取。
