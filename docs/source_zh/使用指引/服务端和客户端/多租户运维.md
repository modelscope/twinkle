# 多租户运维

## 配置可观测性

本地和自托管都按[训练运维启动步骤](https://github.com/modelscope/twinkle/tree/main/cookbook/observability#start-the-training-operations-dashboard)部署。
这套 Compose 运行 Collector、Tempo、Loki、Mimir 和 Grafana，并使用持久存储。
将 `telemetry.otlp_endpoint` 指向 Runtime 可访问的 Collector。按部署需要配置
保留周期和存储后端，示例保留 30 天数据。Mimir 的 TSDB 和工作目录使用受支持的块存储。
限制对 Collector 和 Redis 的访问，并启用 Grafana 登录认证。

所有 Runtime 进程使用相同的 `TWINKLE_TELEMETRY_USER_ID_KEY`，该随机密钥独立于
`TWINKLE_TOKEN_SALT`。未配置密钥时，按用户归因和 Redis 快照暂停。轮换后会生成新指纹，
既有遥测和已归属的旧会话继续使用原指纹，直到保留期结束或会话重建。
Checkpoint 目录沿用原有规则。

## Redis 权限

为 Grafana 配置独立只读账号，连接 Runtime 使用的 Redis 数据库。
配置看板和 ACL 时，三把键都要带上实际的 `persistence.key_prefix`。
以下示例适用于空前缀、Redis 默认数据库。

```text
ACL SETUSER twinkle-grafana reset on >DEPLOYMENT_SECRET ~admin:index:sessions ~admin:index:trainings ~admin:index:sampling +get
```

通过密钥管理服务提供密码。用 Grafana 数据源实查三把运维键，验证同一账号读业务键、
写入以及用 SCAN 或 KEYS 枚举都会被拒绝。Runtime 的清理 leader 按
`metrics_update_interval` 定时刷新，默认每 15 秒刷新。快照含生成时间，
TTL 为三个刷新周期并向上取整到秒。空快照的行列表为空、计数为零。
无 Token 请求在用量和明细中统一归为「未归属」，可用 `unassigned` 筛选。

## 找训练和排查故障

1. 先选时间范围，在 **Current trainings** 或 **Recent training activity**
   找到训练。**Training snapshot** 显示上次刷新和筛选前的当前训练数。
   快照已刷新且计数为零表示当前没有训练。计数大于零、筛选后的表格为空表示无匹配。
   **Unavailable** 表示快照缺失或已过期。数据源错误表示读取 Redis 失败。
   历史日志和 Trace 仍可单独查询。
2. 点击 **Training ID**，打开该训练在所选时间段的 **Training task logs**。
   用 **Log outcome** 找失败、超时或拒绝。需要查看更长的日志时，从面板菜单进入 **Explore**。
3. 展开日志点 **View trace**，或打开 **Runtime task traces** 找对应任务。
   执行 span 展示排队、执行、结果和错误类型。已知任务 ID 时，在 Tempo 查
   `{ span.twinkle.task_id = "req_..." }`，也可在 Loki 查
   `{service_name="runtime-service"} | twinkle_task_id = "req_..."`。
   Span 的 **Logs for this span** 按任务 ID 找日志。
   从 **Links** 打开 **Node GPU utilization** 或 **Node CPU utilization**，
   查看执行时所在节点的资源曲线。

## 查看租户用量和资源

- **User fingerprint prefix** 支持完整指纹或前缀，可从任务 trace 的
  `twinkle.tenant_fingerprint` 复制。**Base model** 和指纹筛选训练和用量。
  **Training ID** 筛选训练与诊断区。**Resource node** 筛选节点资源。
  队列深度汇总所有租户和模型。
- 用量只计已受理的训练计算和普通采样。重试重放只计一次。输入 Token 取受理时已有的
  token ID 数，执行秒数是各副本任务执行时长之和。区间总量用 Prometheus
  `increase()` 估算，每条时序至少需要两个样本。心跳、结果轮询和原始 HTTP 429 分开查看。
- 部署设置请求速率和输入 Token 速率两条参考线。Grafana 对所有租户用相同参考线，
  按五分钟速率高亮。
- CPU 和 GPU 按节点及采集目的地上报一次，进程 RSS 按进程上报。
  GPU 面板按节点和 UUID 显示物理卡。确认模型独占设备后再归因整卡用量。
- **Drilldown → Traces** 使用 Tempo local-blocks 按服务等属性汇总 span 的速率、
  错误和耗时。**Drilldown → Logs** 用于浏览服务和标签。
  **Last Runtime metric received** 用于判断指标上报是否及时，日志和 trace 各自核查。

## 验证部署

确认 Runtime 的指标、日志和 Trace 到达后端，核对保留周期，并在重启后查询已保存样本。
验证 Grafana 认证、Redis 权限和设备标识。使用 Twinkle 和 Tinker 客户端经部署的 API
地址验证会话创建、心跳、采样和结果领取。
