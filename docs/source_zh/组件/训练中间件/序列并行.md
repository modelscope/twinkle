# 序列并行 (SP)

Transformers SP 沿 token 序列维度切分输入，通过 Ulysses 和可选的 Ring 通信完成注意力计算。每个模型持有独立的 `SequenceParallel` context；进程级包装器在调用时选择当前模型的 context。

## 配置

```python
from twinkle.model.transformers.strategy.sequence_parallel import SequenceParallelConfig

config = SequenceParallelConfig(enabled=True, ulysses_size=None)
```

`ulysses_size=None` 时从 DeviceMesh 推导。旧的 `gather_logits` 配置已删除，是否收集完整输出由输出规则与当前 loss 的声明决定。

```python
from twinkle.utils import DeviceMesh

# 8 个设备，两个 SP=4 组。
mesh = DeviceMesh.from_sizes(dp_size=8, fsdp_size=1, ulysses_size=4)
```

## 处理流程与职责

1. Processor 处理张量转换、拼批、普通 padding，并通过 `is_padding_free()` 提供 batch 布局查询；它不接收或调用 SP strategy。
2. 模型包装层区分模型输入与 loss 输入；strategy 在 prepare 阶段切分 labels 等明确声明的局部字段。
3. 模型 forward hook 按规则 pad/split input_ids、inputs_embeds、position_ids 及扩展模型输入。attention_mask 保留全局布局；SDPA 对单样本也构建或补齐全局 padding mask。
4. 注意力包装器进行 Ulysses/Ring 通信，并调用配置选择的注意力后端。
5. 模型侧 `postprocess_task_outputs()` 完成任务处理：embedding 的末 token 池化与归一化、分类/reranker 池化，或普通 token loss 所需的 SP 汇聚。
6. Processor 的 `unpack_packed_sequences()` 将已经恢复全局序列的张量拆回逐样本布局，供 loss 使用。

这里的两类 postprocess 有不同职责：模型侧解释任务输出和执行 SP 通信；Processor 只恢复数据布局。

## 字段声明的归属

- `data_format/sequence_fields.py` 定义 `DataKeySpec` 类型和 provider 声明接口，不维护全局字段大全。
- `processor/fields.py` 就近维护 Processor 已支持的文本、多模态、router replay、控制参数和拼批/恢复规则。raw 图片/视频先由模板编码；内部 `length` 元数据不传给模型。
- `model/transformers/strategy/sequence_parallel/data_keys.py` 维护 SP 的默认执行规则与 batch-local 集合，不把图片像素或控制参数当成 token 序列切分。
- 模型 adapter 和 loss 分别声明自己的扩展字段。

Processor 的规则不安排 SP 操作。SP 开关不会改变自定义 loss 字段是否被保留、拼批或分区。

```python
from twinkle.data_format.sequence_fields import DataKeySpec

# loss-only 输入，默认保持全局；packed 时按样本恢复。
input_key_specs = (DataKeySpec('token_targets', pad_value=-100),)

# 模型 forward 参数，明确安排 SP 操作。
model_input_key_specs = (
    DataKeySpec('token_features', split_dim=1, stage='forward',
                pad_at='forward', split_at='forward'),
)
```

`pad_at/split_at` 可取 `prepare`、`forward`、`model_internal`、`router_replay` 或 `None`；`need_pad/need_split` 是只读推导属性。`stage` 是字段分类，包含 `auxiliary` 和 `output`，不等同于执行时机。

## Loss 为什么需要声明

普通 CE 使用默认收集的 `logps`。PPO value loss 或自定义 loss 可能读取其他序列输出，SP 不能从任意 Python loss 代码中推断这些需求。

- `input_key_specs/output_key_specs` 描述字段布局、模型参数归属，以及可选的并行操作；即使 SP 关闭，Processor 仍消费这些布局规则。
- `sp_gather_keys` 指定当前 loss 必须拿到完整序列的输出。它是当前调用的必需项，缺失输出会报错；字段规则的 `gather_at='loss'` 则表示该输出存在时执行默认汇聚。
- `require_values` 告诉 Transformers 包装层生成逐 token 的 `values`，随后 PPOValueLoss 请求收集它。
- `sp_input_key_specs/sp_output_key_specs` 保留此前声明名称的兼容读取；新代码使用公共名称。

PPOValueLoss 使用的声明如下：

```python
require_logps = False
require_values = True
sp_gather_keys = ('values',)
output_key_specs = (
    DataKeySpec('values', split_dim=1, side='output', stage='output', autograd=True),
)
```

字段 schema 定义如何处理张量，当前 loss 的必需输出声明定义这次计算需要什么。不会无条件 gather 完整词表 logits；fused CE 的 hidden-state 路径单独处理。只在最终 loss 使用的 completion_mask、loss_scale 及默认自定义 target 保持全局。

## 注意力后端

| 后端 | 实现范围 |
|---|---|
| FlashAttention2 / FlashAttention3 | 共用 SP 包装和 packed/varlen 数据处理，实际内核由模型配置选择；具体依赖和设备能力需分别满足 |
| SDPA | 支持普通非 packed batch；padding-free/packed 输入明确拒绝 |
| 派生 Ring | 已接入 FA2/FA3 后端分发，要求 batch_size=1；FA3 路径不支持 dropout 和 ALiBi |

代码接入不代表每种设备/依赖组合均通过训练验收。FA3 的运行时验证应单独记录；不能用 FA2 的测试结果代替。

## 模型特殊处理与 Megatron

Qwen3-VL 的 DeepStack/mRoPE、Qwen3.5 的 GatedDeltaNet、MoE router auxiliary loss 由对应 adapter 配置，使用所属模型的 context。

本页描述 Transformers SP。Megatron 的 CP/TP-SP 是另一条执行路径：embedding 仍由 `MegatronEmbeddingPatch` 池化，分类/reranker 仍在 Megatron 的 forward_step 中处理；CP 重建继续使用 `postprocess_tensor_cp()`。两者共用 Processor 的拼批和 packed 恢复，因此共享路径需要单独回归，不能用 Transformers 训练通过代替 Megatron 整网验收。

分布式运行前需要初始化 `torch.distributed`；SP 大小与注意力头数共同决定 Ulysses/Ring 拓扑。
