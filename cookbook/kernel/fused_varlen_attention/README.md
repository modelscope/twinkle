# 变长因果融合注意力（Ascend NPU）

`twinkle.kernel.ops.fused_varlen_attention` 把 padding-free/packing 训练所需的「分段因果注意力」
在昇腾上落成**一次内核调用**：输入是一条把所有文档首尾相接的 `[T, H, D]` 序列和累积长度
`cu_seqlens`，输出与「逐文档独立做因果注意力」完全等价，文档之间不互相看见。

## 为什么需要这个算子

仓库既有的 padding-free/packing 路径把「必须使用 flash-attention 实现」写成了硬门槛，例如
`src/twinkle/model/transformers/strategy/sequence_parallel/__init__.py` 在 `padding_free` 且
注意力实现不是 flash 时直接 raise，`zigzag_ring_attn.py` 直接 import
`flash_attn.flash_attn_interface`。昇腾上没有 flash-attn，这些路径在 NPU 上无法运行。仓库里只有
定长 SDPA，Liger 的昇腾后端（`ops/backends/_ascend/ops/`）也没有任何因果注意力内核，
因此这是一个真实缺口，而不是对已有实现的改写。

## 用法

```python
from twinkle.kernel.ops.fused_varlen_attention import fused_varlen_attention

# 两条文档：512 + 300 token 拼在一起，8 个 query 头，4 个 kv 头（GQA）
out = fused_varlen_attention(q, k, v, [0, 512, 812])          # -> [812, 8, D]
loss = out.sum()
loss.backward()                                                # dq/dk/dv 由同一算子给出
```

框架侧接入（仓库标准形态：逻辑 target + `KernelChoice`，与 `sdpa_attention` 同构）。
本算子**不进** `DEFAULT_KERNEL_CONFIG`——它只在 padding-free 拼接输入下生效，默认挂载会无条件
覆盖 `flash_attention_2` 分发名，因此在需要时显式启用：

```python
from twinkle.kernel import DEFAULT_KERNEL_CONFIG, kernelize
from twinkle.kernel.registry import KernelChoice

kernelize(model, {**DEFAULT_KERNEL_CONFIG,
                  'npu_varlen': KernelChoice(op='fused_varlen_attention', backends=('npu',))})
```

随后把模型的注意力实现名指向 `flash_attention_2`（只有该实现名会让上游模型把 `cu_seq_lens_q`
透传给注意力函数）。直接调用 HF 模型时把 `cu_seq_lens_q` 作为模型 kwargs 传入；使用
`TransformersModel` 时，`InputProcessor(padding_free=True)` 会从每段重置的 `position_ids`
自动构造这些参数，dense FlashAttention 与 GDN 路径共用这一逻辑。拿不到分段边界的调用自动回退
原生 SDPA。HF 适配层对单文档直接使用原生 causal SDPA，避免没有 packing 收益时仍承担 TND varlen
开销；多文档才进入融合 varlen 内核。完整可运行示例见本目录的 `bench_e2e.py`。

## 等价语义

- 第 `i` 个文档的 token 只能看见本文档中位置不大于自己的 token（标准因果）。
- GQA/MQA：`Hq % Hkv == 0`，kv 头按 `Hkv -> Hq` 分组共享。
- 多文档反向由同一融合内核给出，调用方不需要逐文档循环；HF 单文档快路径由原生 SDPA 给出。

## 基线与指标定义

### 基线是哪几个

本 PR 的融合算子是**纯新增**：既有代码只在 `src/twinkle/kernel/ops/__init__.py` 登记算子，
并由 `InputProcessor` 为 dense packed 输入补齐 varlen 元数据；packed + SDPA 会显式拒绝，避免静默算错。
`DEFAULT_KERNEL_CONFIG` 不含它，`src/` 下没有默认调用方，因此既有 padded 训练行为不变。

基线因此只能是「**main 分支在同一配置下能做到的最好**」。昇腾上 main 只有 `sdpa_attention`
一个注意力算子（`src/twinkle/kernel/config.py:112`），它没有分段边界参数，要算「多篇文档拼在一起、
文档之间互不可见」只能靠 4D 掩码；仓库里 padding-free 的路径在 NPU 上会直接抛错
（`src/twinkle/model/transformers/strategy/sequence_parallel/__init__.py:853`），也就是说这条能力
在 main 上并不存在。于是下面三张单算子表各自回答不同的问题：

| 表 | 基线是什么 | 回答的问题 | 有没有「少算词」的成分 |
|---|---|---|---|
| ① 同样输入、同样词数，只换内核 | 现有算子 + `T×T` 块对角掩码 | 这个内核本身值不值 | 没有 |
| ② 补齐布局 vs 拼接布局 | 现有算子 + 补齐矩阵 + 4D 掩码 | 训练里换过来能快多少 | 有 |
| ③ 附录 | 逐文档掩码 / 逐文档因果 / 整段因果 | 内核的天花板在哪 | 部分有 |

端到端那张表用 ② 的口径：同一个模型、同一批文档、同一初始化权重（用参数哈希校验过）、
同一优化器与步数，只换布局与注意力实现。

### 基线有没有真的在 main 上跑过

有。把 `f8a975f` 的 `src/` 单独签出到另一个工作区，用一个只跑基线、不 import 本目录任何东西的脚本，
在两条 `src` 上各跑一遍同一串长度的 6 篇混合批：

| | main `f8a975f` | 本分支 |
|---|---|---|
| 单步耗时 | 299.3 ms | 295.4 ms |
| 每秒有效词 | 2865.0 | 2902.7 |
| 峰值显存 | 11028 MB | 11028 MB |
| 10 步 loss 曲线 | — | 与 main 逐点一致（6 位小数） |
| 拼接算子 | 不存在（`ModuleNotFoundError`） | 存在 |

差异 1.3% 属测量噪声；基线算子 `sdpa_attention/npu.py` 在两个工作区里 md5 相同（`901dbe31…`）。
8 篇混合批（128–1536 长尾）在两边都 OOM（24.9 GB 打满）——**这是补齐布局的性质，不是本分支引入的**；
同一批次改用拼接布局是 11824 MB、6996 有效词/秒，而 main 上连这条路都不存在。

### 指标怎么算

- **前向 / 前反向耗时**：`torch.npu.Event` 计时，预热 3 次后取 `iters=10 × repeats=5` 的中位数；
  只包住算子调用本身，不含建模、优化器、数据搬运。
- **加速比**：基线耗时 ÷ 本算子耗时，同一进程、同一测量窗口内。
- **峰值显存**：`torch.npu.max_memory_allocated()`（已分配字节，不是缓存池占用），每次测量前
  `reset_peak_memory_stats()`，取一次前反向的峰值。
- **掩码显存**：块对角掩码张量本身的字节数，即 `T×T×元素大小`（半精度 2 字节、单精度 4 字节）。
- **loss 曲线最大绝对差**：两种布局逐点算出的 loss（按 token 求和的交叉熵 ÷ 有效 token 数）
  逐点相减取绝对值最大。不是曲线拟合，是同一批权重、同一批数据下第 1..N 步的逐一对照。
- **有效 token 数（监督 token）**：参与损失的位置数——文档边界与补齐位置都记忽略，因此它不含
  补齐出来的词，两种布局下完全相同。
- **token/s**：有效 token 总数 ÷ 预热后的测量窗口。用有效 token 归一而不是「步/秒」，因为两种布局
  的物理词数不同，按每秒步数比会把补齐的浪费藏起来。
- **物理词浪费**：1 − 拼接后词数 ÷ 补齐后词数（同一批文档、同一随机种子）。
- **前向注意力占单步**：`--profile` 用设备事件包住每层注意力的**前向**调用，累计 28 层 ÷ 单步耗时；
  **不含反向**，不能当作注意力在整步里的全部占比。

## 正确性

```bash
pytest tests/kernel/ops/test_fused_varlen_attention.py -q   # 20 个 CPU 用例 + 28 个 NPU 用例
```

判据：前向输出与 `dq/dk/dv` 对齐「逐文档 SDPA」的精确参考（同一批数值上采样到 FP32 后计算），
FP32 用 `rtol=1e-4 / atol=1e-5`，BF16 用 `rtol=1.6e-2 / atol=1e-2`。

BF16 反向在长序列上会有极少数元素站在 `atol` 边界，因此 BF16 另设**显式越界元素预算**
（`BF16_OUTLIER_BUDGET = 8`、`BF16_MAX_ABS = 4e-2`），`rtol/atol` 本身不放宽。
实测分布（6 组形状，越界元素数）：

| 场景 | 一致（0 越界） | 有越界 |
|---|---|---|
| 512/300/1024/77、2×1024、33/1/256、2048+512 | 全部 4 个张量 | — |
| 16×64（dim 32） | out/dk/dv | `dq` 2 / 131,072 |
| GQA 16/4 2×1024 | out/dq | `dk` 1、`dv` 1 / 1,048,576 |

GQA 那 1 个 `dv` 元素在对精确参考时越界，**原生 BF16 实现自身也有 1 / 1,048,576 同类越界**；
`16×64` 的 2 个 `dq` 元素最大差 1.64e-2（阈值 1e-2 + rtol）。这类越界来自 `dv = P^T @ do`
上千项求和在两种分块顺序下的抵消放大，`inner_precise` 取 0/1/2 实测完全无差别。

## 单算子性能（A2 910B4 单卡，中位数）

这是**新增算子**，所以下面按「没有它的时候怎么办」来对照。昇腾上今天能算对「多篇文档拼在一起、
文档之间互不可见」的写法只有一种：用 twinkle 已支持的 `sdpa_attention`
（`src/twinkle/kernel/config.py:112` 把逻辑名 `sdpa` 指到 `twinkle/kernel/ops/sdpa_attention/npu.py`）
再加一张 `T×T` 的块对角掩码。下面第 ① 张表就是把这个写法和本算子放在**同一个拼接输入、同样词数**
上比较——只换内核，不换布局、不省一个 token。

## 端到端训练（两份代码各跑一遍）

口径：把 main 的 `f8a975f` 的 `src/` 单独签出成一个工作区，用一个只依赖 `src/`、不 import 本目录

同样的步数与优化器）。基线用补齐布局 + `sdpa_attention`，本分支用拼接布局 + 本算子。

  不是训练漂移。

**关于倍数的稳定性（必须一起看）**：上面三行是固定批次，可复核。如果像早期版本那样用随机抽样
生成批次，同一个配置换一组随机长度，倍数会在 1.1–2.4× 之间跳——原因是补齐布局的代价随批次里
**最长那篇**的平方增长，而最长篇是随机抽的；拼接布局在这个规模附近几乎是平的。所以随机抽样单跑
一次不能当结论，本表一律用固定批次。

**loss 噪声底**：同一份代码、同一批次连跑两次，loss 逐点最大差也在 1.1e-3 量级（昇腾上定点归约顺序
不同）。所以表里的 1.6e-3–3.1e-3 和「同代码重跑」基本同量级，判据是曲线形状与逐点差都落在这个底噪附近。

复现（两份代码各一次，`$SRC` 换成 main 工作区或本分支的 `src`）：

```bash
PYTHONPATH=$SRC python e2e_two_checkout.py --layout padded   --lens 128,96,512,224,160,320,96,384 --steps 10      # 基线（main 上可行）
PYTHONPATH=$SRC python e2e_two_checkout.py --layout packed   --lens 128,96,512,224,160,320,96,384 --steps 10      # 本分支（main 上导入即报错）
```

`cookbook/kernel/fused_varlen_attention/bench_e2e.py` 是同一套对照的批次化版本（支持随机长度分布、
`--profile` 统计、单布局运行），便于扫不同长度分布；它的读数同样受上面说的「最长篇」敏感性影响。

## 昇腾调用上的三个坑

1. **因果掩码必须显式传入**。本版本的 `npu_fusion_attention` 会忽略 `sparse_mode` 与
   `next_tockens`：只传 `sparse_mode=3`、不给 `atten_mask` 得到的是**非因果**注意力
   （实测最大误差 3.31，且还更慢），必须给 `atten_mask`。
2. **掩码尺寸与模式的组合只有一种前后向都能跑**：`2048×2048` 上三角布尔掩码配
   `sparse_mode=3`。用 `(T, T)` 掩码配 `sparse_mode=0` 时前向正确，但反向报
   `aclnnFlashAttentionUnpaddingScoreGrad failed, error code 16`；掩码尺寸配合错误时反向数值不可信。
3. `actual_seq_qlen` 只接受 `list[int]`（累积长度，非每段长度），传张量会被 op 直接拒绝。
   训练路径（注意力接口直连 `npu_fused_varlen_attention`）按「张量对象 + `_version`」缓存上一次
   的转换结果，同一批的 28 层共用一次主机同步，就地改写张量会让缓存自动失效；直接调
   `fused_varlen_attention` 时仍需逐次校验边界，每次一次同步。

以上第 1、2 条由 `npu._verify_vendor_semantics` 在每台设备首次调用时用 8 token / 2 文档的
小例子自检（容差 1e-4），CANN 一旦改语义就直接抛错，而不是让训练静默算错。

## 已知限制

- 只支持因果注意力；非因果请用 `backend='torch'`（逐文档 SDPA 参考实现）。
- 不支持 dropout、滑动窗口、跨文档空段。
- `[1, H, S, D]` 的 padding-free 输入要求 batch=1；多 batch 请在数据侧先拼成单序列。
- 块掩码上限为 `2048 × 64` 个 token 的总长（见 `npu.BLOCK_MASK`）。
- 单段长序列（1 × 8192）比原生融合因果慢约 1.24×：块掩码的 2048 粒度换来的是「跨文档不互相
  看见」，没有分段可省的场景下这笔开销就是纯损失。
